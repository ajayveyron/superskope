3. Why other cheap offers did not win
  • RamNode Lite: $3/month, 1 vCPU / 2 GB / 20 GB / 500 GB transfer, but IPv6 only. Cloudflare Tunnel handles inbound access; it does not supply outbound IPv4 for every WAHA, media or package endpoint. This needs end-to-end IPv6 validation or priced NAT before calling it a complete replacement. No NAT service is assumed free. Primary pricing.
  • Google’s free e2-micro: 1 GB RAM, selected US regions, 30 GB standard disk and only 1 GB outbound/month. Ordinary IPv4 adds $0.005/hour, about $3.65 for 730 hours, before traffic and backups. Too constrained to recommend as this stack’s dependable free home. Free limits · Memory · IP billing.
  • Hetzner: its current public cloud page marks the cost-optimized range unavailable. Old CX/CAX price lists are not proof that a cheap instance can be ordered. Its regular range is not the lowest-cost choice verified here. Current availability.
  • Render free: no persistent disk and idle spin-down. Static/serverless hosting alone cannot preserve this always-connected Docker engine, local SQLite and scheduler. Free service limits.

4. Size and architecture, checked against the repo

Start with 2 vCPU, 4 GB RAM and 40–80 GB disk. The existing 2 GB VM works: one read-only sample showed WAHA at 271 MiB and the hub at 22 MiB, excluding the OS, panel, tunnel and peak loads. WAHA itself recommends 2 CPU / 4 GB even for one account. WAHA requirements.

Current private directories total roughly 6.7 MB; the WAHA image alone is 3.11 GB. Allow room for Linux, two image versions, SQLite growth, logs, media and backups. Keep 20% free, rotate logs and alert on disk/memory pressure. No browser engine, managed database, load balancer or Dietboite build is needed.

The current noweb-arm-2026.10.1 is linux/arm64, suitable for Oracle A1. Netcup/Lightsail x86 need the verified same-release noweb-2026.10.1 linux/amd64 image. Pin the corresponding digest and retain NOWEB; do not emulate ARM or change engine/version during migration. Node 24 and the plain JS/static panel are portable. Session restoration across architectures still needs a controlled cutover test. ARM manifest · amd64 manifest.

India latency: Mumbai/Hyderabad should generally beat Singapore, then Europe, then the US for users in India; this is a geographic expectation, not a measured SLA. Europe is reasonable for schedules and explicit Send actions, but adds a round trip to status and administration requests. Test from the actual Dietboite backend and Indian connection before cutover. Cloudflare cannot remove the origin-server distance.

5. What the full cost includes

  • Persistent storage: use the included server disk for data/, sessions/ and media/. No separately billed volume is required.
  • Backups: automate encrypted off-site state backups to private R2 Standard, retaining seven daily and four weekly versions, provided the entire retained set stays under 10 GB. Free tier: 10 GB-month, 1 million writes and 10 million reads; free egress. Beyond that: $0.015/GB-month, $4.50/million writes and $0.36/million reads, with billing-unit rounding. Example: 30 GB retained costs $0.30/month for storage above the free 10 GB. Account-wide allowances may already be used. R2 pricing.
  • Consistency: hourly SQLite online backups plus a coordinated, briefly stopped hub/WAHA copy for daily complete state. Run outside send windows. Test restoration with outbound sending blocked. Keep backup encryption recovery material off the Mac too. Netcup snapshots alone are not off-site backups. Optional Lightsail snapshots cost $0.05/GB-month of stored snapshot data; 20 GB costs $1, outside the base total. Snapshot pricing.
  • Network and domain: included IPv4 avoids paid NAT. Use the existing named Cloudflare Tunnel and wa.ajaypawriya.com, with only API 3011 exposed. Tunnel/DNS/TLS add $0 on the free plan. Domain purchase is $0 incremental; existing annual renewal still continues, at the registrar’s unverified rate. Cloudflare Tunnel.
  • Software: Linux, Docker Engine, Node, SQLite and cloudflared need no paid subscription for this setup. WAHA has been free across features since 2026.6.1; no mandatory Plus or per-message fee applies to the pinned release. Donations are optional. This remains unofficial WhatsApp access, with disconnection/account-restriction risk. WAHA fees.

6. Recommended deployment

Netcup Lite 1 + existing Cloudflare Tunnel + encrypted R2 backups. The extra ≈€1.82/month before tax over nano buys 4 GB RAM and matches WAHA’s recommendation. Choose nano only when the smallest bill matters more than spare capacity. Choose Lightsail Mumbai when Indian hosting and avoiding a six-month commitment justify $12/month.

Dietboite backend → Existing HTTPS API → Cloud Linux host → WhatsApp

Run WAHA and hub with Docker Compose. Run the panel and cloudflared as Linux systemd services, plus backup timers; replace all Mac LaunchAgent/Lima dependencies. Store application files in a stable server path and adjust bind mounts. Keep 3010/3011 bound to loopback and 3012 private. Use an on-demand SSH forward for the panel at http://localhost:3012; its current host/origin checks already accept that address. The laptop is needed only while administering, never to keep messages running.

Keep the current primary WhatsApp phone. The cloud becomes the linked-device server; it does not replace the phone’s registered account. The phone need not stay continuously online, but retain it, use it regularly and keep it available to relink. Moving the host should not require a new number; session recovery may still demand a fresh QR scan. WhatsApp linked-device rules.

7. Migration sequence, for a separately approved task

  1. Freeze a known version with the feature thread. Re-read its handoff and capture the agreed files; this repo has no initial commit. Include in-progress command configuration/history only at an explicitly agreed checkpoint. Recheck prices and orderability, then obtain production approval before provisioning or changing live state.
  2. Prepare an empty destination. Install Linux, Docker/Compose, Node 24, cloudflared and systemd units. Pull the matching pinned image. Verify storage, firewall, DNS, outbound connectivity and empty/fake-engine tests. Do not copy/start the linked session yet; leave hub workers and cloud tunnel disabled.
  3. Quiesce the Mac. Temporarily block client send/group-action requests and disable command handling. Record enabled schedules privately and pause them. Drain in-flight operations; inspect uncertain results instead of retrying. Unload the runtime/panel/tunnel LaunchAgents so they cannot restart; stop hub and WAHA gracefully. Confirm all are down before enabling any cloud sender.
  4. Take the final consistent copy. Transfer the whole stopped data/, sessions/, media/, agreed code/static files, existing .env and the named-tunnel credential/config files over encrypted SSH. Preserve SQLite journal/WAL files if present; never copy only the main database from a live writer. Preserve schedule/run/send IDs, idempotency records, command queues and group-action history. Check hashes and SQLite integrity without printing records or secrets. Restrict secrets to mode 0600; fix Linux file ownership.
  5. Restore with automation held. Keep schedules paused and commands disabled. Inspect queued commands and classify stale/uncertain work before re-enabling; do not blindly replay the queue. Verify the internal WAHA webhook targets http://hub:3011/webhooks/waha with the existing HMAC secret. Retain API keys and linked-device state. Do not run setup routines that regenerate sessions or secrets.
  6. Switch once, then verify. Start only the cloud WAHA/hub and confirm connection privately. If needed, relink once from the existing phone while the Mac stays stopped. Start the cloud connector for the existing named tunnel only after the Mac connector is down. Check authenticated status, anonymous rejection, history and signed inbound events. Request explicit authorization for any real test text/PDF/group action.
  7. Resume deliberately. Preserve prior enabled/paused choices. Resuming an overdue recurring schedule advances to its next future occurrence; expired one-offs need a new agreed time. Normally the worker may retry pre-submission failures for 15 minutes, then skip; uncertain submitted sends must never retry automatically. Review migration-window occurrences rather than sending catch-up batches. Re-enable approved commands after queue reconciliation.
  8. Prove independence and rollback safety. Test a cloud reboot and a backup restore with sending blocked, and confirm the cloud API works with Mac connectors/processes disabled. Leave Mac startup disabled after acceptance, retaining an encrypted rollback copy. If rolling back after cloud activity: stop cloud workers/tunnel first and copy the latest cloud state back before starting the Mac. Restoring an older backup loses later idempotency history; quarantine pending work and reconcile WhatsApp before resuming.

A single VPS can still fail. Backups support recovery, not instant failover. A second active WAHA/hub against the same phone or copied SQLite state is not a safe availability strategy.
