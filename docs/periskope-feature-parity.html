F1 · Real foundation

One linked phone, group text/PDF/image sending, persistent text schedules, signed inbound events and bounded group-admin actions. Local evidence

F2 · Core replacement gap

Shared inbox, 1:1 messaging, team identities, access rules, tickets and assignments are missing. These underpin Periskope’s support workflows. Periskope reference

F3 · AI has a narrow job

SuperSkope interprets group-admin requests. It has no knowledge retrieval, conversation summaries, self-learning or customer handoff. Periskope reference

F4 · Integration gap

WAHA → SuperSkope events work. SuperSkope → client webhook subscriptions do not exist. Engine acceptance is also not a reconciled delivery/read receipt. Periskope reference

F5 · What to prioritize

For the internal workflow

The project explicitly defers the inbox. Keep that decision unless the objective changes. The most relevant additions are scheduled attachments, downstream webhooks, delivery/read reconciliation and an operator view of group actions and command failures. Add per-client API keys before giving more applications access.

For a full Periskope replacement, the dependency order is different:

  1. Conversation foundation: durable chat/message records, history sync, 1:1 and group inbox, media display, message search and receipt reconciliation.
  2. Team workspace: authentication, users, per-chat access, assignments, private notes, labels and quick replies. Add multiple phones if needed.
  3. Support operations: tickets, tasks, business hours, SLA tracking and meaningful team analytics.
  4. Automations and outreach: rules, workflows, outbound webhooks, managed bulk campaigns, templates and advanced schedules.
  5. Advanced parity: knowledge base, AI handoff, self-training, HTTP/MCP tools, richer integrations, calling and packaged clients.

This is a proposed dependency order, not an approved implementation plan or schedule. A cloud move removes the Mac uptime dependency but does not close these feature gaps.

Existing work worth preserving

Durable idempotency, explicit unknown outcomes, no automatic retry after uncertain submission, current-admin checks and scope validation support the internal use case. The Dietboite adapter is documented as locally implemented and tested, not production-deployed. These are useful custom capabilities; this review does not claim Periskope lacks equivalents.

Verification and limits

Verified this review: source inspection of all hub modules and routes, frontend dispatch and panel proxy; official Periskope documentation fetched on Mon 16 Nov 2026; 29/29 baseline backend tests passed against fake engines before concurrent memory edits appeared; three isolated screen captures.

Not re-tested live: message sending, group changes, AI provider execution, recipient-device behavior or a logged-in Periskope account. Earlier live-test results are documented in README and DEVELOPMENT, not presented as new verification.

Concurrent work: Uncommitted edits to commands.mjs and ai-commands.mjs, plus new conversation-memory.mjs, appeared during the review. Source inspection shows persistent account/group/admin-scoped exchanges and compact action-history summaries. This work was not re-tested or confirmed running, so it is not credited as verified parity. It does not change the missing knowledge-base, self-training or general chat-summary findings.

Residual uncertainty: Periskope availability may vary by plan or rollout. Official docs establish advertised/documented capability, not account entitlement or production reliability. Basic group actions have mixed live coverage: create/add/settings were previously checked; remove/promote/demote remain automated-test-only, and a real second-admin natural-language request remains unverified.

Scope: product functionality, not a security audit, load test, price comparison or cloud deployment. No credentials, private databases or customer messages were inspected. No application code or runtime configuration changed.
